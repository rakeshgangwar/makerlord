# MakerLord — Design Spec: the UI

**Date:** 2026-07-29
**Status:** Approved design, pre-implementation
**Covers:** the web app across all seventeen stages — shell, postures,
renderers, the finding surface, bench mode, and the bridge install story

Depth is deliberately uneven: **Phase 1 stages (①–⑥) are specified to build
from; stages ⑦–⑰ get their surface defined and their detail deferred** to the
specs that will design those stages. §5 is the map that keeps the information
architecture honest across all seventeen.

Implements the experience described in
[../../user-journey.md](../../user-journey.md).

---

## 1. The shell: web-first, with a local bridge

**Decision D39.** The app is a web app. `maker-bridge` (ACP host spec §2)
supplies what a browser cannot.

```
                      browser — the product
        ┌───────────────────────┴───────────────────────┐
        │                                               │
   server-side                                    maker-bridge
   hosted agent, toolchain,                       BYO agent, serial fallback,
   git, renderers, ngspice                        local clone, offline bench
        │                                               │
        └──────────── optional, installed once ─────────┘
```

**Why web-first**

D34 already made the project a hosted git repo and D37 already put the native
toolchain server-side — KiCad at ~2 GB plus an ESP32 toolchain at ~2–3 GB is not
a download. Most of the app is therefore a client of things that are already
remote. A desktop shell would add native packaging and signing for three
platforms to buy local access to compute that isn't local.

And the thing we most need to learn is cheap in a browser: **four people
building a circuit from a written guide** (roadmap §7) needs a URL, not an
installer.

**Web Serial is less of a constraint than D14 suggested.** It ships in Chromium
desktop browsers, so a Chrome or Edge maker flashes at stage ⑦ with no install
at all. The bridge is the fallback for the rest — and the path for makers who
want their own agent, their own clone, or bench work in a garage with bad wifi.

> ⚠️ **One unresolved fact underneath this.** This spec assumes Chromium only,
> with Firefox and Safari needing the bridge.
> [references.md](../../references.md) records Firefox as supporting Web Serial,
> from an earlier pass. **They cannot both be right, and the answer changes how
> often the bridge is needed** — a minority fallback or a majority path. Resolve
> before the UI implementation plan; §11's prompt table is what changes.

**Rejected — desktop-first (Tauri):** buys native serial, filesystem and
toolchain access. Two of those three we don't want locally (D37), and GPL
bundling makes the third legally awkward: ngspice and Freerouting are GPL, and
bundling them into a shipped app triggers distribution obligations that running
them server-side does not.

**Rejected — both shells from day one:** doubles the surface of this spec and
every one after it, to serve a preference we haven't yet observed anyone having.

## 2. Information architecture

Three levels, and the middle one is what stops seventeen stages becoming
seventeen products.

```
┌ project ──────────────────────────────────────────────────┐
│ ┌ stage rail ─┐ ┌ workspace ────────────┐ ┌ artifacts ───┐│
│ │ ① idea    ✓ │ │                       │ │ project.json ││
│ │ ② feas.   ✓ │ │   posture-driven      │ │ requirements ││
│ │ ③ req.    ● │ │   (one of four)       │ │ architecture ││
│ │ ④ arch.     │ │                       │ │ …            ││
│ │ …           │ │                       │ │              ││
│ └─────────────┘ └───────────────────────┘ └──────────────┘│
│ ┌ finding strip — always visible, never agent-authored ───┐│
│ └──────────────────────────────────────────────────────────┘
│ ┌ conversation ────────────────────────────────────────────┐│
│ └──────────────────────────────────────────────────────────┘
└───────────────────────────────────────────────────────────┘
```

**The stage rail** shows all seventeen, grouped by the four phases, with state
per stage: not started / in progress / complete / blocked. It is a map, not a
wizard — makers loop and backtrack (roadmap §1), and a rail that only moves
forward would lie about the work.

**The workspace** takes one of four shapes. Not seventeen.

**The finding strip** spans the frame and is present in every posture. §7 is
about why.

**The conversation** is always reachable and never the whole screen except in
Converse. The agent is a collaborator on the artefact, not the artefact.

## 3. Four postures, not seventeen modes

| Posture | Stages | Shape |
|---|---|---|
| **Converse** | ① ② ③ ④ | Chat, low density, one question at a time |
| **Inspect** | ⑤ ⑨ ⑩ | Canvas, high density, zoom and pan |
| **Bench** | ⑥ ⑦ ⑧ ⑬ | Full screen, huge type, hands busy, phone-friendly |
| **Decide** | ⑪ ⑫ ⑭ ⑮ | Report plus a button that costs money |

Keeping to four is what makes a seventeen-stage product learnable. Each posture
is a layout and a set of interaction defaults, not a separate app:

**Converse** — the conversation takes the centre; the workspace is a
right-hand summary of what's been settled so far. Requirements appear as they're
confirmed. **A blank canvas is intimidating; a text box is not** — stage ① opens
with a prompt, not an empty document.

**Inspect** — the canvas takes the centre with the conversation collapsed to a
strip. Zoom, pan, layer toggles, selection linked across views: clicking a part
in the schematic highlights it on the breadboard and in the BOM. That linkage is
free because both are projections of one model (D2), and it's the most visible
payoff of that decision.

**Bench** — one step, everything else dimmed. Type large enough to read at arm's
length across a desk. Touch targets sized for a hand that has just put down a
pair of pliers. §8.

**Decide** — a report, a number, and one irreversible action. The number is
framed, never bare (§9).

---

## 4. The three-region frame in practice

The regions are responsive rather than fixed. On a laptop all three are visible;
below ~1100 px the artifact panel becomes a drawer; below ~700 px the layout
collapses to whichever region the posture makes primary — conversation in
Converse, canvas in Inspect, the step in Bench.

**The finding strip never collapses.** It shrinks to a severity summary with a
count and expands on tap, but it is never absent. A layout in which a BLOCKER
can be off-screen is a layout we don't ship.

**Two rows deserve their treatment stated now**, because getting them wrong
loses people at exactly the emotional troughs (user-journey §7):

**⑪ Manufacturing** — the number arrives with framing or not at all. *"£61 at
qty 1, £14 at qty 100. The cheapest single change that moves this is X."* A bare
figure is the difference between a reality check and an ending.

**⑮ Compliance** — leads with the ~80% already satisfied because the constraints
were applied at ④, ⑨ and ⑩ (D33), then the gap and what it costs. It must feel
like *"you're most of the way there"* rather than a wall, because that is
factually what the design has produced. And it must never imply compliance (D31).

## 6. Renderers

Every renderer is a **deterministic projection of `project.json`** (D2). None of
them takes an image from the agent; none of them is generative.

| Renderer | Output | Notes |
|---|---|---|
| Schematic | SVG | Shares its layout engine with the KiCad generator (D27) |
| Breadboard | SVG | Hole-accurate, from the Fritzing geometry |
| Block diagram | SVG | Stage ④, from the architecture facet |
| Waveform | Canvas | From simulation CSV, client-side, zoomable |
| 3D | GLB via WebGL | Board and enclosure; no plugin |
| Reports | Markdown | Cost, DFM, fit, ERC/DRC |

**The schematic layout engine is shared, and that's not an optimisation.** D27
committed to generating hierarchical KiCad schematics; the same placement and
routing logic drives the in-app renderer. One engine means the schematic a maker
inspects at ④ is topologically the schematic they open in KiCad at ⑨ — and one
engine's bugs, not two.

**Selection is model-level, not view-level.** Clicking `R3` selects a model
entity; every open view highlights it. Adding a view later inherits linkage for
free.

## 7. The finding surface

The safety architecture reaches the screen here, and this section is the reason
BYO agents are acceptable at all (ACP host spec §6).

**Findings are rendered by the client from engine data. Never from agent
prose.**

The strip is populated by `ToolResult` payloads carried verbatim through
`SessionEvent` and by the UI's own `check_*` calls. The agent does not write it,
cannot summarise it, and cannot reorder it. An external agent that says "that
finding looks conservative" has said something the maker can read — next to the
finding, still on screen, unchanged.

```
┌────────────────────────────────────────────────────────────┐
│ ⛔ BLOCKER  LED_NO_SERIES_RESISTOR          verified  [why] │
│    LED1 anode connects to 5V with no current limit.         │
│    → Add a resistor. At 5 V with a 2.0 V forward drop,      │
│      220 Ω gives 13 mA.                                     │
└────────────────────────────────────────────────────────────┘
```

Each card carries **severity, rule id, provenance badge, the claim, and a
remedy**. `[why]` expands the derivation — this is where progressive disclosure
serves the maker rather than the model.

**There is no dismiss control.** D3's `Finding` has no suppression field and the
tool surface has no `dismiss_finding`; the UI completes the line. A blocker
leaves the screen when the circuit changes and the rule stops firing. That is
the only way.

**Provenance is visible, because it bounds severity.** `verified` and `computed`
can reach BLOCKER; `sourced` tops out at WARNING; `inferred` and `assumed` top
out at NOTE. Showing the badge makes the system legible: a maker who curates a
part sees the check that depends on it get stronger, which is a genuinely
satisfying feedback loop and the honest explanation for why some warnings are
soft.

**Severity is never carried by colour alone.** Icon, label and colour together.
This is an accessibility requirement everywhere and a safety requirement here.

## 8. Bench mode and the phone

Bench is a posture, not a separate app — the same routes, responsive. The phone
companion is "the app on a phone", which is what keeps it thin by design.

- **One step.** Everything else dimmed, not hidden — the maker needs to know
  there are twelve more.
- **Huge type**, readable at arm's length with a board on the desk between.
- **Measurement entry takes a number, never a checkbox** (D15). A numeric keypad,
  units pre-filled, the predicted value *not* shown until after entry. Showing
  the expectation first turns a measurement into a confirmation.
- **Camera** for stage ⑬ and photo verification.
- **Wake lock** while a build is in progress. A screen that sleeps mid-step
  during a two-handed operation is a small betrayal.

**Mid-turn steering has a UI.** *"Wait, I don't have that resistor"* at step
seven is a first-class action, not an interruption to apologise for (agent
runtime §10). The step stays on screen while the agent responds.

## 9. Gates and handoffs

Two moments in the arc need the UI to say something out loud.

**The measurement gate (⑥)** is the emotional core of the product. It should
feel like **preflight, not paperwork** — deliberate, faintly ceremonial. A
distinct full-width state, the instruction in the imperative, one number to
enter, and a visible consequence when it passes. Not a modal to dismiss.

**The ownership handoff (⑨)** — at the PCB the maker opens KiCad and takes the
wheel. D35 made this an explicit one-way transition, and **it must be said out
loud in the UI at the moment it happens, or it will feel like the tool broke.**
Not a footnote: a stage-level statement of what we stop doing (generating
layout), what they now own (routing, placement refinements), and what we still
do (re-verify with DRC, offer netlist updates the way KiCad's own
update-from-schematic works, preserving placement).

It coincides with cloning locally (user-journey §2), so it reads as one
transition rather than two.

**Tier opt-in for mains (D32)** is a Decide-shaped moment wherever it occurs: a
statement of what opening the tier means, what rules it *adds*, and an explicit
acknowledgment. Never a checkbox in a settings panel. And mains-on-breadboard is
refused at every tier — that refusal is a finding card with no path forward, and
the UI must not imply one exists.

## 10. Concurrency and live state

D34 means two writers: the web app and a local clone.

**Optimistic locking surfaces as a specific, non-alarming state.** A refusal
with `STALE_PROJECT` renders as *"this project changed elsewhere — reload to see
the latest"*, with a reload action. Not an error dialog; not a silent overwrite.

**The web app refuses to write a diverged tree and says "pull first." It never
force-pushes** (user-journey §2). Git already solved this and we do not
reimplement it.

**The session event stream** arrives over SSE from the hosted agent, or over the
localhost WebSocket from the bridge. Both deliver `SessionEvent`; the UI has one
consumer. Reconnection replays from the last event id.

## 11. The bridge, as the maker experiences it

Nobody should meet the bridge before they need it.

| Trigger | Prompt |
|---|---|
| Flashing on Firefox or Safari | "Your browser can't talk to serial ports. Install the bridge, or use Chrome." |
| Choosing a BYO agent | "Your own agent runs on your machine. Install the bridge." |
| Cloning locally at ⑨ | Offered alongside the handoff, as one transition |

Install is a download and a run. **Pairing is one code, entered once** (ACP host
spec §7) — the bridge prints it to its own console, which is also the moment the
maker learns it has a console worth looking at when something fails.

**Degradation is explicit, never silent.** When the bridge is expected but
absent, the affected controls are disabled with the reason attached. A flash
button that does nothing is worse than one that says why it can't.

## 12. Stack

**SvelteKit.** Fine-grained reactivity suits a streaming event feed; SVG is
first-class rather than something to escape into `dangerouslySetInnerHTML`; and
the runtime cost is low for an app that will render large SVGs and a WebGL scene
on the same page. For a solo builder plus agents, less ceremony per component is
a real schedule effect.

**React is the reasonable alternative** and would win on ecosystem depth and on
hiring. If either of those becomes the binding constraint, this is a
substitution at the component layer — the renderers are SVG-and-canvas
generation over a typed model and are not framework-shaped.

Supporting choices: **`three.js`** for GLB (stage ⑩), **Playwright** for
end-to-end, **Vitest** for units. All ⚠️ pending version verification in
[references.md](../../references.md).

## 13. Accessibility

The product is aimed partly at fourteen-year-olds and used partly at a bench
with occupied hands. Both push the same direction.

- **Colour is never the sole carrier of meaning** — critical for severity (§7)
- **Keyboard reachable throughout**, including the canvas: selection, pan and
  zoom have key equivalents
- **Type scales generously in Bench**, and the scale is a user setting
- **Findings are live regions.** A new BLOCKER is announced, not just drawn
- **Touch targets sized for a hand holding a probe**, not a mouse at a desk

---

## 14. Testing

**Renderer golden images.** A fixture `project.json` in, an SVG out, compared
byte-wise. Deterministic projection (D2) means this is a real equality assertion,
not a perceptual diff — and it will catch layout-engine regressions that reach
the generated KiCad schematic too, since they share the engine (§6).

**End-to-end with no LLM.** Playwright drives a seeded project through the tool
surface directly — the golden script from the tool-surface spec §7, with a
browser on top. Front door to build gate, deterministic, no model in the loop.

**The finding-surface assertions**, which are the safety tests at this layer:

- a BLOCKER is visible in every posture and at every breakpoint
- **no control anywhere in the app dismisses, hides or downranks a finding** —
  the DOM-level analogue of the tool-surface registry invariant
- a finding's provenance badge matches its severity ceiling
- agent prose claiming a finding is resolved does not remove the card

**Bridge-absent states.** Every control that needs the bridge renders its
disabled reason when it isn't there.

## 15. Scope

**In:** `packages/ui` — the shell, stage rail, four postures, three-region
frame, finding surface, all six renderers, bench mode, the gate and handoff
moments, concurrency states, the bridge prompts, and the tests above. Stages
①–⑥ built; ⑦–⑰ have their surface reserved per §5.

**Out:**

- **Stage-specific detail for ⑦–⑰**, which belongs to the specs that design
  those stages. §5 is the contract they build against.
- **Bridge packaging, signing and auto-update** — real work, and its own spec.
- **Marketing site, auth, billing, onboarding** — none of it is the product.
- **A CAD editor.** We generate and verify; KiCad and CadQuery own editing
  (roadmap §8).
- **Native mobile apps.** The phone companion is this app, responsive.

**This is more than one implementation plan.** The natural split is three:
the shell and Converse posture (stages ①–④, pairing with the front-door plan),
Inspect and the renderers, and Bench with the gate. The finding surface belongs
to the first — it is the piece everything else assumes.
