# MakerLord — Design Spec: Simulation

**Date:** 2026-07-29
**Status:** Approved design, pre-implementation
**Covers:** stage ⑤ — ngspice from our netlist: operating point, transient and
small-signal AC

Depends on the netlist derivation from
[the prototype spec](2026-07-28-makerlord-design.md) and on the requirement
model from [the front door](2026-07-29-front-door-design.md).

---

## 1. What this is, and what it is not

**Simulation catches design errors before parts are bought.** It is the cheapest
verification in the arc — nothing has been ordered, nothing can burn.

It is **not** the DC solver. `predict_dc` already exists, and the two must not
merge:

| | `predict_dc` | Simulation |
|---|---|---|
| Purpose | Predict multimeter readings for the measurement gate | Find design errors |
| Speed | Milliseconds, always available | Seconds, on request |
| Fidelity | Linear DC, deliberately crude | Nonlinear, time- and frequency-domain |
| Failure mode | Must never fail — it gates a physical build | May fail to converge, and says so |
| Runs | Server or bridge, always | Server (D37), or a local ngspice if present |

The gate depends on `predict_dc` being fast and always-available. Coupling it to
a solver that can fail to converge would make a safety gate contingent on
numerical luck.

## 2. The pipeline

```
project.json ──► SPICE netlist ──► ngspice ──► raw output ──► traces + findings
   (D2)          sim/circuit.cir    batch      parsed         CSV, PNG, report
```

Every step is a projection or a parse. Nothing is generated by a language model.
The agent chooses *what to simulate and why*; the numbers are ngspice's.

**Artifacts:**

```
sim/
├── circuit.cir            ←  generated netlist, readable and hand-runnable
├── results/
│   ├── op.csv             ←  node voltages, branch currents, device power
│   ├── tran-startup.csv   ←  one file per named run
│   ├── ac-filter.csv      ←
│   └── *.png              ←  derived from CSV, for the report and the repo
└── report.md              ←  what was run, what it found, what it assumed
```

**CSV is canonical; PNG is derived.** The waveform viewer (UI spec §6) reads CSV
client-side and is zoomable; the PNG exists so the repo and the technical file
contain something a human can open in five years.

`circuit.cir` is deliberately readable and runnable by hand. A maker who knows
SPICE should be able to check our work, and a maker who doesn't has a file to
paste into a forum when they ask for help.

## 3. The model problem, which is the whole spec

**A simulation is exactly as good as its device models**, and our measured
electrical coverage of the Fritzing corpus is **2–4%**
([corpus-findings.md](../../corpus-findings.md)). Most parts arrive with no
SPICE model at all.

Pretending otherwise would produce the worst possible artefact: a confident,
precise, plotted, wrong answer. So the project's existing provenance rule
governs simulation results too.

### D43 — simulation results inherit the provenance of their weakest model

| Model source | Provenance | Severity ceiling |
|---|---|---|
| Manufacturer SPICE model, checked in | `verified` | **BLOCKER** |
| Model derived from datasheet parameters we curated | `computed` | **BLOCKER** |
| Vendor model of unclear origin | `sourced` | WARNING |
| Generic idealisation (ideal diode, linear resistor at nominal) | `assumed` | **NOTE** |
| No model, part omitted or stubbed | `assumed` | **NOTE** + `SIM_MODEL_MISSING` |

**A run's provenance is the weakest model in the loop**, not the average. One
idealised part caps the whole analysis, because that part is exactly where the
error will be.

This generalises the same rule the front door applies to requirements and the
rule engine applies to findings. It also produces the same satisfying loop: **a
maker who curates one part's SPICE model upgrades every check that depends on
it.** The provenance badge in the UI (UI spec §7) is where that becomes visible.

### The MCU boundary, stated once and enforced

**We simulate the analogue envelope around the microcontroller. We do not
simulate the microcontroller.**

A digital part is represented as a behavioural stub: a supply-current sink with
declared active and sleep values, and I/O pins as voltage sources with declared
drive strength and output impedance. Everything about that stub is `assumed`
unless the maker or the corpus supplies measured numbers.

This is honest and it is also sufficient for the questions that actually bite:
does the rail sag when the radio transmits, is the level shifter biased
correctly, will this resistor cook, does the sensor front-end have the corner
frequency the requirement asked for. None of those need the firmware to run.

Firmware-in-the-loop co-simulation is **explicitly out of scope** (§9).

## 4. The three analyses

### 4.1 Operating point — `.op`

The baseline, and the one that runs on every `sim_run` regardless of what else
was asked for. AC analysis needs it anyway (ngspice linearises around it), and
transient starts from it.

Produces node voltages, branch currents and per-device power. Each is checked
against the part's ratings from the safety overlay:

- `SIM_ABSMAX_EXCEEDED` — a device beyond an absolute-maximum rating
- `SIM_POWER_DISSIPATION` — dissipation above the package rating, with the
  derating curve applied where we have one
- `SIM_NODE_UNEXPECTED` — a node more than a declared tolerance from the value
  the architecture's power budget predicted

That last one is a cross-check between two independent derivations of the same
number — the architecture's arithmetic and ngspice's solve. When they disagree,
one of them is wrong and the maker should know before the parts arrive.

### 4.2 Transient — `.tran`

Time-domain. Startup, switching, rail sag under load step, inrush.

The hard part is not the analysis, it is **the stimulus** — see §5.

- `SIM_RAIL_SAG` — a supply rail below a part's minimum operating voltage at any
  point in the window, which is the failure that a static power budget cannot see
- `SIM_STARTUP_TIMEOUT` — a rail that never reaches its target within the window
- `SIM_INRUSH` — peak current beyond a source or connector rating

### 4.3 Small-signal AC — `.ac`

Frequency response. Filters, sensor front-ends, and gain or phase margin where a
feedback loop exists.

Requires an AC-annotated source and a circuit that linearises meaningfully
around its operating point. Where it doesn't — a comparator, a switching
converter — we say so rather than plotting a curve that means nothing:

- `SIM_AC_NOT_APPLICABLE` — a strongly nonlinear block in the signal path,
  reported as a NOTE about the *simulation*, not about the circuit
- `SIM_AC_CORNER_MISMATCH` — measured corner frequency outside a numeric
  requirement's bounds (§6)

## 5. Stimulus, and being honest about where it comes from

A transient run needs to know what the circuit is *doing*. That information does
not exist in the netlist.

```ts
interface Stimulus {
  id: string;
  target: string;              // a net or a source reference
  kind: 'dc' | 'pulse' | 'pwl' | 'sine' | 'load_step';
  params: Record<string, number>;
  provenance: 'stated' | 'derived' | 'assumed';
  rationale: string;           // why these numbers
}
```

Three sources, and they carry different weight:

- **`derived`** — from the requirements or the architecture. "One reading per
  hour" (requirements) plus a radio module's declared active current
  (architecture) derives a load step. This is the good case and the agent should
  reach for it first.
- **`stated`** — the maker declared it. Also good.
- **`assumed`** — the agent guessed a duty cycle, a rise time, a load. Legal,
  labelled, and **caps the run's severity at NOTE** by §3's rule, exactly as an
  idealised model would.

`SIM_STIMULUS_ASSUMED` fires as a NOTE listing every assumed stimulus in a run,
with its rationale. It is the prompt for the maker to replace a guess with a
number and watch the analysis get stronger — the same loop as curating a model.

**A firmware-driven pin becomes a `PULSE` or `PWL` source with a declared duty.**
That is the MCU boundary (§3) expressed as a stimulus, and it is `assumed` until
the maker says otherwise or the firmware stage derives it.

## 6. Simulation discharges requirements — the first stage that can

The front-door spec gave every `Requirement` a `consumedBy` array — the
anti-orphan guarantee that a stated number is used by something downstream.
Until now, "used" has meant "constrained a design decision."

**Simulation is the first stage that can automatically check one.**

```
requirement   corner frequency ≤ 10 Hz          (numeric, D30)
      │
      ▼
sim_check_requirements ──► .ac sweep ──► measured corner 7.4 Hz  ──► PASS
                                                                     │
                                            recorded with the run id,
                                            the trace, and the provenance
```

`sim_check_requirements` walks every requirement whose metric a simulation can
measure, runs the analysis, and records a verdict against the run.

| Requirement shape | Analysis |
|---|---|
| Frequency corner, bandwidth, gain | `.ac` |
| Rail voltage under load, ripple | `.tran` |
| Quiescent current, device dissipation | `.op` |
| Startup time | `.tran` |
| Battery life, cost, size, temperature range | **none** — not simulable |

The last row matters as much as the others: the tool must say *"this requirement
cannot be checked by simulation"* rather than quietly passing it or quietly
ignoring it. An unchecked requirement is a known gap; a silently unchecked one
is a false sense of coverage.

**Verdict severity obeys §3.** A requirement failed against idealised models is
a NOTE saying the design may not meet it and the models are weak — not a
BLOCKER. A requirement failed against verified models is a BLOCKER.

## 7. Convergence, and never lying about it

Convergence failure is the practical reality of SPICE and the single most likely
way this stage produces a wrong impression.

**A run that did not converge produced no result. It did not produce a pass.**

The retry ladder, applied automatically and recorded in the report:

```
1. default options
2. gmin stepping                     .options gmin=1e-10, stepped
3. source stepping
4. relaxed tolerances                reltol 1e-3 → 1e-2, abstol raised
5. integration method                trapezoidal → gear
6. give up
```

Each rung that succeeds is recorded — **a result obtained at rung 4 is reported
with the tolerances that produced it**, because a solution found only at relaxed
tolerance is a weaker claim than one found at default.

Giving up emits `SIM_NO_CONVERGENCE`: a NOTE **about the simulation**, never a
finding about the circuit. It names the rungs tried, and where ngspice reported
the failure, which is usually the most useful debugging pointer available.

**The distinction is the whole point.** "Your circuit is wrong" and "our tool
could not solve your circuit" are completely different statements, and conflating
them either scares makers away from correct designs or reassures them about
broken ones.

## 8. Tools

Four additions to the registry (tool-surface spec §5), taking the catalogue from
32 to 36 — still well below the threshold where tool search earns its complexity.

| Tool | Gated | What it does |
|---|---|---|
| `sim_stimulus_set` | no | Declare or replace a stimulus, with provenance and rationale |
| `sim_run` | no | Run named analyses; returns run id, verdict summary, findings |
| `sim_results` | no | Fetch traces for a run — progressive disclosure, not inlined |
| `sim_check_requirements` | no | Check every simulable requirement; record verdicts |

**None of them gate.** Simulation is advisory by nature — it happens before
anything physical exists, so there is no unsafe action to refuse. Its findings
flow into the same rule pipeline and *those* can block a downstream gated action
in the usual way.

`sim_run` returning traces inline would put megabytes of numbers in a prompt.
It returns a summary and a run id; `sim_results` fetches a named trace,
downsampled by default. Same progressive-disclosure move as
`parts_search` → `parts_get`.

## 9. Scope

**In:** SPICE netlist generation from the project model, the model-provenance
rule and its severity ceilings, the MCU behavioural stub, `.op` / `.tran` / `.ac`
with their findings, the stimulus model, requirement discharge, the convergence
ladder and honest failure, four tools, CSV and PNG artifacts, and the report.

**Out:**

- **Firmware-in-the-loop co-simulation.** The most differentiated thing in this
  space and by a distance the hardest — a research project, not a slice. The MCU
  boundary (§3) is the deliberate alternative, and it answers most of the
  questions makers actually have.
- **Monte Carlo and tolerance analysis.** The obvious v2, and genuinely valuable
  for anything going to production — a design that works at nominal and fails at
  5% resistor tolerance is a real and common failure. Deferred because it
  multiplies run count by the number of samples and needs tolerance data the
  corpus doesn't yet carry.
- **Thermal simulation.** Dissipation numbers, yes; temperature rise, no.
- **RF and controlled-impedance behaviour.** Named in roadmap §6 as something we
  don't pretend at, and that holds here.
- **Replacing `predict_dc`.** §1.
- **The waveform viewer** — UI spec §6. This produces the CSV it reads.

## 10. Testing

**Known-answer circuits**, asserted numerically within tolerance. These are the
tests that prove the pipeline rather than the plumbing:

| Fixture | Analysis | Assertion |
|---|---|---|
| Resistive divider | `.op` | Node voltage exact to 0.1% |
| LED with series resistor | `.op` | Current within 5% of hand calculation; power finding fires on an undersized resistor |
| RC low-pass | `.ac` | −3 dB corner within 2% of `1/(2πRC)` |
| RC charging | `.tran` | Voltage at one time constant ≈ 63.2% |
| Load step on a soft supply | `.tran` | `SIM_RAIL_SAG` fires with the sag depth |

**Provenance ceiling tests.** The same fixture run twice — once with a curated
model, once with a generic idealisation — asserting that an identical numeric
outcome produces **BLOCKER** in the first case and **NOTE** in the second. This
is the executable form of D43 and it is the test that matters most.

**A convergence-failure fixture.** A deliberately stiff circuit that fails the
whole ladder, asserting: `SIM_NO_CONVERGENCE` emitted, no circuit findings
emitted, no requirement recorded as passed, and the rungs tried listed in the
report.

**A missing-model fixture.** A part with no SPICE model at all: stubbed,
`SIM_MODEL_MISSING` emitted, run capped at NOTE, and the part named.

**Requirement discharge.** A project whose requirement is checkable and one whose
requirement is not, asserting a verdict in the first case and an explicit
"not simulable by this stage" in the second — never silence.

**Netlist golden files.** A fixture `project.json` in, a `circuit.cir` out,
compared exactly. Deterministic projection (D2), so equality is the right
assertion.

**No ngspice in unit tests.** The generator and the parser are tested against
golden files; ngspice itself appears only in the integration layer, where a
missing binary skips loudly rather than passing quietly.
