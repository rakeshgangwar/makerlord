# MakerLord Firmware Implementation Plan (stage ⑦)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build stage ⑦ — the firmware model facet, the D48 GPIO curation, the D46 role-symbol contract with its lint, the seven-rule cross-check family and its release-blocking danger corpus, deterministic scaffold codegen, the `arduino-cli` compile gate, six new registry tools (37 → 43), and the bench-posture ⑦ lens with WebSerial flashing behind the power gate (D47).

**Architecture:** One new package, `@makerlord/firmware`, depending on parts/circuit/project (not on tools — the six `fw_*`/`check_firmware` ToolDefs live in `@makerlord/tools` and call into it, the sim precedent). The firmware *facet types* live in `@makerlord/project` beside the other facets; derivation, rules, lint, codegen and the compile runner live in the new package. Flashing is browser-only (D37): no server flash tool exists.

**Tech Stack:** TypeScript (strict), Node 22, pnpm, Vitest. `arduino-cli` as a subprocess in the integration layer only. Browser: esptool-js (ESP8266) and stk500v1 (Uno) over WebSerial.

**Spec:** [../specs/2026-07-30-firmware-design.md](../specs/2026-07-30-firmware-design.md)

## Global Constraints

- **D46: code never names a pin.** `pins.h` is a pure projection, regenerated on every netlist change; a raw pin literal in the application region is `RULE_FW_RAW_PIN_LITERAL`, a BLOCKER. The lint is a table over pin vocabularies + pin-position call sites, not a C++ parser.
- **D47: flashing is powering.** `fw_manifest` refuses unless the power gate is open. The UI never renders a flash control the engine would refuse.
- **D48: GPIO facets are hand-authored and datasheet-cited** — strap pins and analog domains come from datasheets, never derived from core headers.
- **Roles are derived, never authored.** No tool sets a role's `mcuPin` — the safety property is the absence of the tool (D3/D4 pattern).
- **Behaviors are a closed set in this plan:** `sample`, `threshold`, `drive`, `serial_log`. A kind the engine doesn't know is a validation error, not a fallthrough to codegen.
- **The firmware danger corpus is release-blocking** — the same contract as Tier-1: a failure is a destroyed MCU, not a flaky test. Never weaken it to get to green.
- **No `arduino-cli` in unit tests.** Golden files + canned compiler output; the integration layer skips **loudly** when the binary is missing (the ngspice precedent — a silent skip shipped a wrong model once).
- **`firmware.bin` exists only if compilation succeeded** and carries `compiled` provenance. Serial output is untrusted (`[device output — unverified]`) except the scaffold's structured `SELFTEST` lines.

- [ ] Tests: facet parses; unknown pin names rejected against the footprint; profiles without the facet stay valid

### Task 2: Curate the two MCUs

- [ ] D1 mini: full `gpio` map — A0 divider (`analogMaxV: 3.2`), strap pins D3/D4 (HIGH) and D8 (LOW) with datasheet citations, D0's no-PWM/no-interrupt, `fqbn esp8266:esp8266:d1_mini`, esptool-js flash

- [ ] `curated-manifest.test.ts` extended: an MCU profile (has `fqbn`) must carry a `gpio` facet

### Task 3: The firmware facet (types in `@makerlord/project`)

- [ ] `Behavior` (closed set: `sample`, `threshold`, `drive`, `serial_log`) and `Role` types; zod parse; `project.firmware` optional facet on the model
- [ ] Tests: unknown behavior kind rejected; roles round-trip; a project without the facet stays valid

### Task 4: Pin-plan derivation (`@makerlord/firmware`)

- [ ] `derivePinPlan(circuit, defs, profiles, behaviors)`: walk intent nets joining the target MCU's pins to part pins → role candidates named from the part/block served; modes from behavior kinds (`sample`→ANALOG_IN/INPUT, `drive`/`threshold.drive`→OUTPUT); role renames preserved across re-derivation; `mcuPin` never settable
- [ ] Unbindable behaviors (no wiring supports the role) reported as data for `RULE_FW_ROLE_UNBOUND`
- [ ] Tests: soil-sensor fixture derives MOISTURE_SENSE→A0 + STATUS_LED→D5; re-derivation after a rewire updates `mcuPin` and keeps the rename; MCU-less circuit is a clean error

### Task 5: The cross-check rules (six model-level)

- [ ] `RULE_FW_OUTPUT_INTO_RAIL` (BLOCKER), `RULE_FW_PIN_CAPABILITY` (BLOCKER), `RULE_FW_STRAP_PIN_CONFLICT` (BLOCKER), `RULE_FW_ANALOG_OVERVOLTAGE` (BLOCKER, uses predicted net voltage), `RULE_FW_INPUT_FLOATING` (WARNING), `RULE_FW_ROLE_UNBOUND` (BLOCKER) — same `Finding` shape, `suggestedFix` on every one
- [ ] Tests per rule: firing fixture + benign twin

### Task 6: The raw-pin lint (D46)

- [ ] `lintApplicationRegion(code, profile)`: vocabulary table (board pin names, `GPIO\d+`, bare small-int in pin-position args of `pinMode`/`digitalWrite`/`digitalRead`/`analogRead`/`analogWrite`/`attachInterrupt`) → `RULE_FW_RAW_PIN_LITERAL` BLOCKER naming the literal and the role to use instead
- [ ] Tests: `digitalWrite(D5, HIGH)` fires; `digitalWrite(STATUS_LED, HIGH)` clean; `delay(500)` (int, not a pin position) clean; comment/string literals clean

### Task 7: The firmware danger corpus 🔒

- [ ] `fw-danger-corpus.test.ts`: one row per §4 rule — OUTPUT-into-rail first — each with the fault, the expected rule, and a benign twin that must stay silent; gate helper asserts BLOCKERs block
- [ ] CLAUDE.md: name it beside the Tier-1 corpus as release-blocking
