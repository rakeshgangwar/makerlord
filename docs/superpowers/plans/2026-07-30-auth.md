# MakerLord Auth Implementation Plan (invites + passkeys)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build D52–D54 — the file-backed user stores, human-minted invites, WebAuthn join/login owned by the UI server, cookie sessions, API user resolution (service-token+header, or per-user token), per-user project scoping with the 404-ownership property, bridge tokens, migration, and the retirement of nginx basic auth.

**Architecture:** A new tiny package `@makerlord/auth` holds the stores and pure ceremony-adjacent logic — imported by BOTH the API server and the SvelteKit server (same host, shared `MAKERLORD_USERS_PATH`). SimpleWebAuthn does the cryptography. The API never sees a cookie (D53).

**Spec:** [../specs/2026-07-30-auth-design.md](../specs/2026-07-30-auth-design.md)

## Global Constraints

- **No passwords, anywhere.** No password field ever enters a schema.
- **Invites are minted by the maintainer CLI only** — no web or agent surface (D52/D51).
- **Ownership is 404, not 403** — existence of another user's project is private.
- **Atomic writes** on every store (temp + rename), the project.json posture.
- **The service token alone never authorizes a project route** — it only vouches for the UI server's user header.
